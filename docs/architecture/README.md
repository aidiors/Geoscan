# Архитектура GeoPlan

GeoPlan состоит из одного Python-приложения и одного React-интерфейса.
Код сгруппирован по задачам предметной области. Зависимости алгоритмов
передаются явно; конкретные реализации выбираются при сборке приложения.

## Сервер

Рабочий код — устанавливаемый пакет `backend/src/geoplan`.
`bootstrap.py` создаёт приложение, `composition.py` собирает зависимости.
Точка запуска — `geoplan.bootstrap:app`.

| Модуль | Ответственность |
|---|---|
| `api` | HTTP-маршруты, обработка ошибок, app factory |
| `domain` | Общие модели координат, парка, миссий, ограничений и диагностики |
| `planning` | Полный процесс, отбор БВС, подготовка кандидатов и отчётов |
| `coverage` | Построение, декомпозиция и сравнение покрытия |
| `navigation` | Геометрия, обход препятствий, Dubins и Hybrid A* |
| `assignment` | Распределение участков между БВС |
| `routing` | Общая модель service/deadhead, связные клетки, ресурсный Split и назначение вылетов |
| `scheduling` | Расписание и вертикальное разведение |
| `airspace` | Применимость ограничений и временные окна |
| `flight` | Время, энергия, площадки, рельеф и аварийный уход |
| `safety` | Независимая проверка итоговых миссий |
| `geodata` | Чтение геоданных и экспорт заданий |

Модели конкретного алгоритма находятся в его `models.py`; общие предметные
понятия — в `domain`. `PlanningError` находится в `errors.py` и не требует
импорта реализации планирования.

`planning/engine.py` сохраняет последовательность расчёта: отбор БВС → покрытие →
кандидаты → распределение → расписание → отчёт и независимый аудит.
Аудит принимает интерфейс проверки экспортов; адаптер задаётся в `composition`.

### Оптимизация групп вылетов

`planning/productive.py` подключён к тому же `build_plan`, которым пользуется
`POST /v1/plans`. Он сохраняет исходный план и проверяет ограниченный пул
до 20 вариантов: ресурсные каталоги, назначения, короткие вылеты,
адаптивный destroy/repair и обмен между критериями. Ресурсный каталог строится
из тех же обязательных галсов, выбранных штатным покрытием; угол и сами
съёмочные проходы не подменяются бенчмарковым сценарием.

Физические стоимости, клетки, Split и назначение находятся в `geoplan/routing`.
Стенд импортирует эти реализации; рабочий пакет не импортирует `benchmarks`.
Метаданные замороженных экспериментов остаются в стенде, за пределами
физической модели приложения.

Каждая альтернатива создаётся штатным построителем миссий: он заново проверяет
нагрузку, реальные площадки, погоду, дальность, АКБ, рельеф и аварийный уход.
Затем применяются обычные окна пространства, разведение, высотные слои и
независимый аудит. Выбор использует исходный критерий с реальным makespan;
непрошедший аудит или худший по критерию кандидат не заменяет проверенный
исходный план. Если исходное разбиение не помещается в АКБ, допустимый
альтернативный план может восстановить расчёт без ослабления ограничений.

`survey_phases.py` отделяет фиксированные съёмочные плечи от соединений.
Новые группы содержат отдельные `SURVEY`/`TRANSIT`; скорости на соединениях
не ограничиваются интервалом фотосъёмки. У исходного плана при сравнении
сохраняются времена движения, но камера и метрики также разделяются по
исходным галсам. Это исключает приписывание транзита полезной съёмке.

Флаг API `productive_routing` по умолчанию выключен для совместимости клиентов.
Интерфейс отправляет его включённым и позволяет отключить для сравнения.
Быстрый режим отключает дополнительный поиск. Для одной области группировка
применяется без ручных маршрутов при 2–400 галсах. `planning/multi_area.py`
сравнивает составные варианты для нескольких областей с общим расписанием
и аудитом; `planning/reassignment.py` повторяет глобальное назначение.
Ограничения и незавершённая квалификация профиля перечислены
в [актуальной передаче](../production-handoff-2026-10-18.md). Размер участка
служит исходному разбиению; при включённой оптимизации группы ограничивает
физический ресурс БВС. Лимит активных БВС соблюдается при обоих способах
назначения. Все алгоритмы пула эвристические.

Радиусы и установленные камеры разрешаются отдельно для каждого БВС.
`survey_adapter.py` строит его физические переходы из общих прямых проходов;
`curved_costs.py` учитывает направления при ранжировании, а рабочий построитель
заново проверяет криволинейную геометрию. `allocation.py` обновляет нагрузки
и стоимости при добавлении вылета, сохраняя каноническую целевую функцию.

Лимиты каталога/назначения ограничивают генерацию, не полное время расписания
и аудита. Поэтому используется ограниченный пул вместо всего исследовательского
перебора. В `optimization.productive_routing` возвращаются выбранный вариант,
число проверенных альтернатив и исходные показатели для сравнения.

### Единое исполнение и камера

`planning/execution.py::AuditedMissionEvaluator` — общий модуль подготовки,
расписания и аудита для приложения и физического стенда OR-Tools.
`AuditedSchedulePortfolio` сравнивает политики очереди и высот; CP-SAT
подключается явно через `assignment_strategy=cp_sat_portfolio` либо политикой
по умолчанию `automatic` для нескольких участков/БВС в критериях срока и баланса
и возвращает
альтернативу только после оценки итогового расписания.

`flight/camera.py` воспроизводит команды камеры на часах стадий.
`planning/photography.py` проверяет стыки: если новый дистанционный триггер
нарушает аппаратный интервал, плоская миссия получает явные точки кадров
через `routing/photography.py`. Маршрут и времена движения сохраняются.
Миссии с рельефом и таким нарушением отклоняются до поддержки вставки кадров
в высотный профиль; проверка не подменяется интерполяцией непроверенных высот.
Общий аудит проверяет интервалы и число кадров (`camera_timing`), а для
явных кадров фиксированных проходов — объединение конечных отпечатков.

Физические отпечатки явных кадров находятся в `flight/photography.py`.
`planning/survey_quality.py` строит дополнительный отчёт; `lateral_overlap.py`
разбивает продольный диапазон по концам проходов и выбирает соседей отдельно
в каждом интервале. Советник `planning/advisor.py` повторно рассчитывает
предложенные условия; изменение высоты требует явного разрешения в запросе.

### Свободное покрытие

После пула фиксированных проходов `planning/freeform.py` сравнивает ограниченный
набор контуров, контурных слоёв с прямым центром и разомкнутых дуг к посадке.
Используется тот же `productive_routing`, без дополнительного режима API.
Проверяются одна RGB-область MSL без рельефа, радиус 0, площадь до 5 км²,
не более 128 вершин и шаг от 10 м. Кандидат покрывает всю область одним
вылетом; для других задач сохраняются штатное покрытие и ресурсное разбиение.

`routing/freeform.py` содержит физическую модель, ориентацию и проверку конечных
кадров, `routing/coverage_patterns.py` — контуры/дуги и прямой центр,
`routing/photography.py` — кадры на точных часах реальной миссии.
Внешние алгоритмы не импортируют orchestration. Стенд использует эти же
реализации; копий алгоритмов и совместимых обёрток нет.

Для каждого из четырёх проходов поиска — не более трёх сочетаний
аппарат/площадки и двух допустимых вариантов до расписания. В каждом
сочетании сохраняется исходный префикс из шести путей; разнообразный пул
расширяет его до 18. Отдельно проверяются дополнительные направления.
Мягкий бюджет 12 с проверяется между сочетаниями каждого прохода:
это не предел полного времени ответа.
До и после расписания защищаются суммарные налёт, camera-off, подход к съёмке
и возврат относительно исходного проверенного плана и лучшего пула
фиксированных проходов. Затем применяется исходная целевая функция.
Статус выбранного свободного покрытия — `heuristic`, область оптимизации —
`freeform_coverage_route_pool`; глобальная оптимальность не утверждается.

Кадры превращаются в явные точки маршрута с точными временами. Поле миссии
`photo_capture_route_indices` задаёт эти позиции; количество согласовано
с `image_count`, один аппаратный clock сохраняется через повороты и короткие
переходы. `safety/freeform.py` повторно проверяет реальные стадии после
расписания: ≥99,99% объединения кадров, ≥99,9% внутреннего коридорного
покрытия, GSD, частоту и физические времена. АКБ, воздух, расписание и
аварийный уход проверяются обычным аудитом. Попарная площадь кадров не стала
обязательным требованием; фотограмметрическая реконструкция не моделируется.

GeoJSON/KML сохраняют позиции кадров; форматы автопилотов используют
одиночные команды `MAV_CMD_IMAGE_START_CAPTURE` (2000) в этих точках,
с последовательными идентификаторами. Средний дистанционный триггер для
таких миссий не подставляется. Протокол —
[MAVLink common](https://mavlink.io/en/messages/common.html#MAV_CMD_IMAGE_START_CAPTURE).

Фабрики и замороженные входы находятся в `backend/scenarios/freeform.py`.
`benchmarks/run_frame_coverage.py` — текущий геометрический драйвер,
`verify_free_coverage.py` — его проверка по архивным исходникам;
`verify_freeform_pipeline.py` — отдельная сквозная проверка HTTP и экспортов.
Локальное изменение времени кадров остаётся исследовательским методом.

Эксперименты находятся в `backend/benchmarks`, фабрики сценариев —
в `backend/scenarios`. Они не включаются в рабочий пакет и контейнер.
Тесты разделены на `unit`, `integration`, `contracts` и `benchmarks`.

`create_app(dependencies, serve_frontend=False)` создаёт HTTP-приложение без
статических файлов. Обычный запуск обслуживает интерфейс из `dist/`.

## Интерфейс

| Каталог | Ответственность |
|---|---|
| `app` | Сборка экрана и тема |
| `features/planner` | Сценарий, обработчики, настройки, запросы, миграции и панели |
| `features/demos` | Каталог примеров, данные и витрина сценариев |
| `features/geodata` | Импорт зон |
| `features/mission-export` | Получение экспортов |
| `widgets/mission-map` | Карта, управление видом и отображаемые слои |
| `shared/api` | HTTP-транспорт, ошибки и типы серверного контракта |
| `shared/geo` | Координаты и вычисления отображения |
| `shared/browser` | Скачивание файлов |

Alias `@/` одинаково настроен в TypeScript, Vite и Vitest. Тесты UI и чистых
функций находятся рядом с проверяемым кодом.
`App` собирает экран, `usePlanner` управляет рабочим сценарием.
Модели редактирования отделены от типов HTTP-контракта.

## Правила зависимостей

1. `domain` не импортирует реализацию алгоритмов и HTTP-фреймворк.
2. Рабочий пакет не импортирует тесты, эксперименты и фабрики сценариев.
3. Алгоритмы не импортируют `planning.engine` и HTTP-маршруты.
4. Между Python-модулями нет циклов импортов.
5. В браузере зависимости направлены от `app` к `widgets`, `features` и `shared`.
   `features` могут использовать другие возможности и `shared`; `shared` использует
   только собственные модули и внешние библиотеки.
6. Между исполняемыми TypeScript-модулями нет циклов. Ссылки только между типами
   не создают исполняемой зависимости.
7. Независимый аудит не заменяется чтением флага успеха построителя маршрута.
8. Новая модель получает владельца по назначению; общий файл всех моделей
   приложения заново не создаётся.

Первые шесть правил и разрешение локальных импортов проверяются автоматически:

```powershell
python scripts/check_architecture.py
npm run check:architecture
uv run --directory backend pytest tests/unit/test_architecture.py -q
```

Проверка Python использует AST, включая относительные и пакетные импорты.
Проверка TypeScript использует парсер TypeScript: учитывает alias, относительные
пути, реэкспорты, строковые динамические импорты и зависимости только между типами.
Произвольно вычисляемые динамические импорты этими проверками не анализируются.

## Сохранение поведения

Структурный рефакторинг выполнен без изменения вычислительных алгоритмов,
HTTP-полей, форматов экспортов и сохранённых сценариев. Сохранены исходные
обработчики запросов и порядок обновления состояния. Типы HTTP пока поддерживаются
вручную; команда [экспорта OpenAPI](../../README.md#проверки) работает без сервера
и сборки интерфейса.

Для проверки переноса сопоставлены AST 637 исходных определений, OpenAPI,
три полных плана и 12 экспортов. Отличия определений ограничены app factory
и новым путём к статике. Контрольные расчёты и контракты совпали с исходными.

Команды полного набора проверок — в [README](../../README.md#проверки),
ручная приёмка — в [чек-листе выпуска](../release-checklist.md).
Локальные E2E в Chrome ограничены системной политикой отладочных подключений;
отдельный запуск E2E настроен в CI. Запуск приложения, статики, расчёт и экспорты
дополнительно проверены в Docker.
