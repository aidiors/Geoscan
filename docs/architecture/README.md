# Архитектура GeoPlan

GeoPlan состоит из Python-сервера и React-интерфейса. Рабочие алгоритмы
получают зависимости явно; реализации выбираются в `composition.py`.
Точка запуска — `geoplan.bootstrap:app`, приложение создаёт `create_app`.

## Сервер

Рабочий пакет находится в `backend/src/geoplan`.

| Модуль | Ответственность |
|---|---|
| `api` | HTTP, ошибки, потоковый ответ, проекты и проверка DEM |
| `domain` | Общие модели парка, геометрии, миссий, высот и ограничений |
| `planning` | Полные стратегии, отбор БВС, кандидаты, сравнение и отчёты |
| `coverage` | Направления проходов, покрытие и декомпозиция |
| `navigation` | Безопасные соединения, видимость, A*, Dubins и Hybrid A* |
| `assignment` | Назначение участков: точный поиск, эвристики, CP-SAT |
| `routing` | Физические стоимости, каталоги групп, ресурсное разбиение и свободные маршруты |
| `scheduling` | Временное и высотное разведение миссий |
| `airspace` | Ограничения, эшелоны и временные окна |
| `flight` | Ветер, время, энергия, рельеф, фазы полёта и аварийный уход |
| `safety` | Независимый аудит итоговых миссий |
| `geodata` | Импорт, экспорт, подтверждение проверенного плана и пакет вылетов |
| `projects` | Документы, версии, переносимые архивы и SQLite-хранилище |

Модели отдельного алгоритма находятся рядом с ним в `models.py`; общие
предметные типы — в `domain`. Ошибки планирования определены в `errors.py`.

## Рабочий pipeline

`api/routes.py` собирает `AuditedPlanningService`: быструю начальную стратегию,
основной расчёт и ограниченный альтернативный Adaptive pipeline.
`PlanningTransport` обслуживает JSON и NDJSON, поддерживает отмену и ограничивает
число параллельных расчётов двумя на процесс.

`planning/engine.py` выполняет отбор БВС → покрытие → кандидаты → назначение →
расписание → аудит и отчёт. `planning/progress.py` сравнивает проверенные
результаты целых стратегий по исходному критерию под одним бюджетом.

- `productive.py` группирует проходы одиночной области.
- `multi_area.py` сравнивает составные планы нескольких областей.
- `cross_area.py` объединяет соседние области в общие вылеты.
- `reassignment.py` повторяет глобальное назначение после перегруппировки.
- `execution.py::AuditedMissionEvaluator` задаёт общий путь подготовки,
  расписания и аудита для сервиса и физических бенчмарков.
- `schedule_portfolio.py` и `assignment_portfolio.py` принимают альтернативы
  после оценки реального расписания и аудита.

Пулы используют штатные построители миссий. Эксперименты импортируют рабочие
реализации, а приложение не импортирует стенд. Подключённые методы, лимиты,
цели и границы модели описаны в [оптимизации](../optimization.md).

### Свободное покрытие

`planning/freeform.py` сравнивает ограниченный набор контуров и смешанных
траекторий. Физическая модель находится в `routing/freeform.py`, генерация —
в `routing/coverage_patterns.py`. Кандидат проходит то же расписание и аудит.
Границы применимости приведены в [описании методов](../optimization.md).

### Камера и время

`survey_phases.py` разделяет съёмку и транзит. `flight/camera.py` воспроизводит
команды камеры на часах стадий. `planning/photography.py` при допустимых
условиях вставляет явные точки кадров, сохраняя аппаратный интервал.
`flight/photography.py` проверяет отпечатки; `planning/survey_quality.py`
готовит дополнительный отчёт, `lateral_overlap.py` проверяет боковых соседей.
Поля часов и кадров описаны в [контракте](../4d-geodata-contract.md).

### Проекты и экспорт

`projects/repository.py` хранит неизменяемые версии в SQLite, а `codec.py`
проверяет переносимый документ. Каталог задаётся `GEOPLAN_DATA_DIR`, локальное
значение по умолчанию — `work/server-data` в корне репозитория.
Docker использует отдельный постоянный volume.

`geodata/release.py` связывает подтверждение с входными данными и неизменным
проверенным выполнимым планом. Автопилотный экспорт и ZIP-пакет проверяют это
подтверждение. Восстановленный архив требует нового расчёта для выдачи таких
заданий. GIS-экспорт доступен отдельно для анализа.

## Интерфейс

| Каталог | Ответственность |
|---|---|
| `app` | Сборка экрана и тема |
| `features/planner` | Рабочий сценарий, парк, настройки, расчёт и прогресс |
| `features/demos` | Каталог примеров и витрина |
| `features/geodata` | Импорт и сопоставление геоданных |
| `features/terrain` | Загрузка, проверка и профиль DEM |
| `features/projects` | Сохранение, версии и перенос проектов |
| `features/mission-export` | Получение экспортов |
| `widgets/mission-map` | Карта и отображение слоёв |
| `shared` | HTTP-транспорт, типы API, геометрия отображения и скачивание |

`App` собирает экран; `usePlanner` управляет сценарием. Модели редактирования
отделены от HTTP-типов. Alias `@/` согласован в TypeScript, Vite и Vitest.
HTTP-типы поддерживаются вручную; OpenAPI выгружается командой из
[README](../../README.md#проверки).

## Правила зависимостей и проверки

1. `domain` не импортирует алгоритмы или HTTP-фреймворк.
2. Рабочий пакет не импортирует тесты, бенчмарки и фабрики сценариев.
3. Алгоритмы не импортируют HTTP и `planning.engine`.
4. Исполняемые Python- и TypeScript-модули не образуют циклов.
5. Зависимости интерфейса направлены от `app` к `widgets`, `features`, `shared`;
   `features` могут использовать другие возможности, `shared` — только свои модули.
6. Независимый аудит не заменяется флагом успешного построения маршрута.

```powershell
uv run --directory backend --locked --extra optimization python ../scripts/check_architecture.py
npm run check:architecture
uv run --directory backend --locked --extra optimization python ../scripts/check_docs.py
```

`backend/tests/` разделён на `unit`, `integration`, `contracts`, `benchmarks`.
Frontend-тесты находятся рядом с кодом; сквозные — в `frontend/e2e`.
`create_app(..., serve_frontend=False)` позволяет проверять API без статики.
Обычный сервер обслуживает сборку из `dist/`.
