ветка `dev/architecture-refactor`, база этой сессии `5f0ea4b`.
Работа остановлена по просьбе пользователя для передачи товарищу.
**Окончательный выбор продакшен-комбинации ещё не завершён.**
Пользователь считает ожидание более пяти минут слишком долгим.
Продолжать без субагентов; не ослаблять физическую модель, качество или аудит.

## Что находится в pipeline

- `coverage/production.py`: кандидат политики по умолчанию. Для нескольких
  областей либо сложной геометрии (>128 внешних вершин или >4 отверстий)
  используется ограниченный поиск направления; для одной простой области —
  Adaptive. Быстрый режим использует минимальный повёрнутый прямоугольник.
  Ограниченный поиск сравнивает направления оболочки и сетку 15°, уточняет
  победителя на ±1°/±2°. Мягкий бюджет 1,5 с на область допускает продолжение
  поиска первого допустимого маршрута. Ручное направление сохраняется.
- `planning/multi_area.py`: продуктивные группы для нескольких областей,
  до 12 подходящих областей по 2–400 проходов, до трёх составных альтернатив.
  Все миссии совместно назначаются, планируются и проверяются; это не слияние
  независимо разведённых расписаний. Исходный проверенный план сохраняется.
- `planning/reassignment.py`: повторное глобальное назначение после изменения
  групп, ограничение 2000 пар участок/БВС, затем ограниченное сравнение CP-SAT.
  Принимается только улучшение итогового критерия после расписания и аудита.
- `assignment_strategy=automatic`: CP-SAT сравнивается для completion/balanced
  при нескольких участках и доступных БВС. Быстрый режим отключает сравнение.
  OR-Tools устанавливается через extra `optimization`, бюджет решателя 2 с.
  Недоступный решатель оставляет исходный вариант. В UI отдельный флажок
  реализации решателя убран; продуктивный поиск остаётся включённым.
- `budget.py`: общий кооперативный бюджет 270 с на построение плана,
  запас 60–90 с перед необязательным поиском, клиент ждёт до 300 с.
  Проверки стоят в вычислительных циклах, но не прерывают отдельный вызов GEOS
  или другую нативную операцию. Жёсткая гарантия wall-clock ещё не подтверждена.
- `navigation/routing.py`: подготовленные запросные контексты безопасных путей,
  ограниченные кеши и A*. Исправлены вершины графа вокруг вогнутых препятствий:
  узлы берутся с внешней границы, запретная геометрия не ослабляется.
  Независимая проверка стоимости использует свежий контекст той же проекции.
- Импорт сохраняет все объекты и даёт уникальные ограниченные по длине ID.
  Нулевые площади диагностируются до тяжёлого расчёта. В UI есть выбор
  отдельных областей, поиск, выбор всех и явное исключение площадей <1 м².
  Демонстрационные ручные маршруты не подмешиваются к импортированным областям.
- Сохранены предыдущие исправления часов камеры, конечных кадров, бокового
  перекрытия, общего исполнения и ускорения назначения. Подробности —
  [в предыдущем отчёте](review-2026-10-18.md). Фазы съёмки/транзита исходного
  покрытия теперь нормализуются и без продуктивного поиска.

## Данные и полученные результаты

Все необходимые исходники, фабрика `backend/scenarios/customer.py` и исходный
KML `reference/hackathon/Границы полетов.kml` находятся в репозитории.
KML содержит 696 объектов: 83 с точно нулевой площадью и 52 положительных
меньше 1 м². В операционную выборку стенда входят 561 объект ≥1 м²;
это явное правило стенда, а не скрытая фильтрация API. Максимальная область
58,61 км², 773 внешние вершины, пять отверстий.

[Сохранённая частичная серия](../reference/benchmarks/production-portfolio-progress-2026-10-18.json)
содержит **11 из 45** запланированных расчётов, SHA-256 исходников и KML,
параметры запуска, метрики, расписания, аудит и выполнимость. Хеши исходников
сверены с передаваемым кодом. Серия прервана пользователем, не считается приёмкой.
Локальные большие снимки запросов/ответов лежат в игнорируемом `work/`;
воспроизведение использует фабрику и отслеживаемый KML.

Пример: восемь близких реальных полигонов, anchor=1, 2,341 км²:

| Критерий | Вариант | Расчёт, с | Завершение, мин | Налёт, мин | Вылеты |
|---|---|---:|---:|---:|---:|
| balanced | bounded | 13,50 | 120,092 | 253,84 | 73 |
| balanced | production | 19,32 | 77,740 | 56,74 | 8 |
| balanced | adaptive_cp_productive | 83,44 | 77,423 | 56,42 | 8 |
| completion_time | production | 19,98 | 32,242 | 86,08 | 17 |
| completion_time | adaptive_cp_productive | 83,52 | 19,683 | 60,98 | 8 |

Округлённое полное время приведено для ориентира, точные значения — в JSON.
Все 11 завершённых планов прошли аудит. Это не означает выполнения срока:
статус `feasibility` записан отдельно, исходные bounded-планы нарушают срок.
Adaptive в completion-сценарии дал существенный выигрыш при ещё допустимом
ожидании; одного balanced-примера недостаточно для решения отказаться от него.
Текущая production-политика — отправная точка, а не доказанно лучшая комбинация.

Условия стенда синтетические: четыре БВС, центральная площадка, камера,
отсутствие ветра. Реальные слои ограничений/препятствий заказчика не подключены.
Peak RSS — накопленный максимум процесса, не память отдельного запроса.
В этой серии не включён `--exports`; экспорт проверяется отдельными тестами.
Старые JSON приёмки относятся к указанным в них хешам и не заменяют эту серию.

## Как продолжить

```powershell
git clone --branch dev/architecture-refactor git@github.com:aidiors/Geoscan.git
cd Geoscan
npm ci
uv sync --directory backend --locked --extra optimization
uv run --directory backend --locked --extra optimization pytest -q
npm test
npm run typecheck
npm run build
```

Повторить частичную серию в новом файле, не перезаписывая доказательства:

```powershell
uv run --directory backend --locked --extra optimization python -u -m benchmarks.production_portfolio pipeline --count 8 --algorithms bounded bounded_productive bounded_cp_productive adaptive_cp_productive production --output ../work/customer-8-repeat.jsonl --exports
```

Дальнейшие приоритеты:

1. Закончить сравнение трёх критериев и anchors 1/3/5. Затем размеры пакета
   32/64/128; дорогой Adaptive запускать выборочно под общим бюджетом.
   CLI поддерживает `--criteria`, `--anchors`, `--deadline`, `--exports`.
2. Проверить полезность портфеля целых планов bounded+Adaptive на небольших
   пакетах, сохраняя лучшего проверенного кандидата и общий бюджет.
   Такого комбинированного портфеля пока нет. Не повторять независимо полный
   бюджет для каждого метода в одном пользовательском запросе.
3. Добавить ветер, разные старт/посадку, ограничения площадок и реальные
   запретные слои; текущий CLI не имеет аргумента ветра. Сравнивать одинаковые
   исходные условия, не менять перекрытие ради победы. Сделать повторы времени.
4. Проверить рекурсивный branch-and-bound при >1000 участках с единственным
   назначением: защита глубины/короткий путь пока не добавлены. Проверить
   конкурентные запросы и память: общего контроля нагрузки пока нет.
5. Проверить таймауты на самых больших/сложных областях. Не возвращать
   непроверенный частичный результат; отдельно оценивать аудит, срок, качество,
   холостой ход, налёт, время вычисления и все четыре экспорта.
6. После результатов выбрать политику и обновить документацию/приёмку.
   Не объявлять глобальную оптимальность. Камера с рельефом и конфликтом
   аппаратных интервалов пока диагностируется, а не исправляется автоматически.
