# Воспроизведение вычислительных экспериментов

Бенчмарки находятся в `backend/benchmarks/`, общие фабрики геометрии —
в `backend/scenarios/`. Они используют рабочий пакет `geoplan` и не входят
в серверный контейнер. Небольшие проверки их корректности находятся
в `backend/tests/benchmarks/` и выполняются обычным `pytest`.

## Запуск

Из каталога `backend/` после `uv sync --locked`:

```powershell
uv run python -m benchmarks.compare_optimizers
uv run python -m benchmarks.compare_coverage_planners
uv run python -m benchmarks.compare_corridor_planners
uv run python -m benchmarks.run_small_radius_geometry
uv run python -m benchmarks.run_coverage_experiments
uv run python -m benchmarks.run_productive_routing --seconds 2 --seeds 3 --oracle-seconds 10
uv run python -m benchmarks.run_productive_routing --suite scale --seconds 2 --seeds 3
uv run python -m benchmarks.run_productive_routing --suite sensitivity --methods split split_reassign --seconds 2
uv run python -m benchmarks.productive_performance
uv run python -m benchmarks.run_productive_routing --suite adaptive --methods adaptive alns_fast --seconds 2 --seeds 3
```

Команда `run_coverage_experiments` сохраняет CSV и JSON в `docs/benchmark-results/coverage-*`.
Это локальные артефакты измерений; каталог исключён из Git. Для сравнения
серий фиксируйте коммит, параметры сценария, версии зависимостей и оборудование.
Время выполнения нужно измерять на целевой машине.

Эксперимент `run_productive_routing` сохраняет `results.json` и `results.csv`
в `docs/benchmark-results/productive-routing-v3-<suite>/`. Второй цикл сохранён
в `docs/benchmark-results/productive-routing-v2-*`, первая серия —
в `docs/benchmark-results/productive-routing/`. В JSON находятся исходные галсы,
назначения и параметры каждого решения. `--tiny-only` оставляет малые контрольные
задачи с точным перебором. `--suite scale` запускает девять задач на 100 км²
с десятью БВС: без ветра, с ветром и с запретной зоной, по трём критериям.
`--suite all` объединяет обе серии. `--methods split split_reassign` позволяет
ограничить набор методов. Параметр `--seconds` задаёт мягкий бюджет поиска для
каждого метода; фактическое время записывается отдельно. ALNS запускается
с seed от `0` до `--seeds - 1`, каждый запуск получает отдельный бюджет.
Одинаковый seed при ограничении по времени не гарантирует побитового повторения.
Для повторного запуска выбирайте новый каталог через `--output`: раннер
отказывается перезаписывать существующий `results.json`. В каждой новой серии
автоматически сохраняются снимок исходников и их SHA-256, время подготовки
и аудита, число геометрических расчётов и признак сохранения baseline.
`--suite sensitivity` сравнивает лимиты внутренней длины 25/50/100/200 км
на одной плоской области 100 км². Для каждого лимита заново строится штатный
baseline; качество съёмки, галсы и запас времени БВС сохраняются.

`--suite adaptive` отделяет размер исходного сегмента от физического времени
вылета. Для девяти больших задач строится сильный эталон: лучший штатный план
среди размеров сегмента 25/50/100/150/200/225/250 км, выбранный по исходному
критерию. В этой серии `maximum_internal_distance_km=null` у всех методов:
ограничением вылета остаётся фактическое доступное время БВС. Старые серии
с численным ограничением длины сохраняют прежние условия.

Подготовка сетки эталонов занимает заметное время и учитывается отдельно.
`--input <results.json>` воспроизводит сохранённые задачи без повторного
построения эталонов; путь и SHA-256 входного файла записываются в результат.
`--cases ...` и `--criteria total_flight_time` ограничивают выборку.
Формат данных проверяется при чтении. Например, после создания новой серии:

```powershell
uv run python -m benchmarks.run_productive_routing --input ../docs/benchmark-results/productive-routing-v3-adaptive/results.json --methods adaptive alns alns_fast --seconds 2 --seeds 3 --output ../docs/benchmark-results/my-replay
```

`regret2_fast` считает изменение подлёта, возврата и переходов при вставке
и обновляет загрузку парка без полного пересчёта каждого кандидата.
Для задач больше 50 галсов рассматриваются шесть ближайших существующих
вылетов; это эвристическое сокращение кандидатов. `alns_fast` использует
тот же набор операций удаления и ускоренный repair. Семантика целевой
функции сохраняется; ускорение не гарантирует улучшения результата.

`adaptive` строит каталог последовательных групп галсов с выбором направлений,
подбирает границы групп по запасу полёта и пробным ограничениям длительности,
затем распределяет их по БВС. Финальное решение сравнивается с baseline
по исходному критерию. Порядок самих галсов фиксирован; глобальная
оптимальность маршрутов и распределения не заявляется.

`productive_performance` сравнивает общий и отдельный для каждого БВС
кэш геометрии на одинаковом фиксированном объёме работы. Выполняются три
повторения с чередованием порядка вариантов; совпадение стоимостей и полного
решения проверяется по SHA-256. Это оценка одного изменения экспериментального
оценщика, а не ускорения всего приложения.

Это экспериментальная модель фиксированных галсов: галс выполняется ровно один
раз, переходы считаются отдельно, каждый вылет возвращается на свою базу.
Время завершения определяется загрузкой БВС с подготовкой между вылетами.
Основной раннер не проверяет расписание конфликтов, рельеф, временные окна
и экспорт. Для расписания, аудита и экспорта есть отдельный адаптер ниже. Критерии сравнения сохраняют порядок приоритетов штатного
распределителя; Split минимизирует только суммарный налёт и проверяется также
на остальных критериях как контроль возможного ухудшения.
`split_reassign` тратит до 60% оставшегося бюджета на Split и затем распределяет
группы от самых длительных к коротким с выбором БВС по исходному критерию.
Результат сравнивается с baseline; сохранение baseline не считается улучшением.
Сводка первой серии — в [отчёте](productive-routing-results.md).

## Группировка и перестройка целых вылетов

`cells` выделяет цепочки соседних параллельных галсов с взаимно однозначным
перекрытием между рядами. Разветвление или слияние завершает участок.
Набор обязательных галсов сохраняется. Несколько порядков обхода участков
сравниваются дешёвой геометрической оценкой; для выбранного порядка каталог
считает безопасные переходы, ветер, длительность и исходный критерий.
Выбор предварительного порядка эвристический, глобальная оптимальность
не заявляется. У непараллельных входов участки состоят из одиночных галсов.

`sorties` пробует удалить целый вылет и вставить все его галсы заново,
а также обменять хвосты двух вылетов, в том числе с реверсом.
Незавершённое восстановление отбрасывается. На удаление выделяется часть
оставшегося времени; счётчики попыток и завершённых восстановлений
разделены. `cells_sorties` сначала выделяет до 80% бюджета, но не более
двух секунд, на `cells`, затем применяет эти операции. Во всех трёх
методах допустимый incumbent защищён исходным критерием.

Пример серии из каталога `backend/`:

```powershell
uv run python -m benchmarks.run_productive_routing --input ../docs/benchmark-results/productive-routing-v3-physical/results.json --cases scale_restriction_physical --methods adaptive cells alns_fast sorties cells_sorties --seconds 2 --seeds 10 --output ../docs/benchmark-results/productive-routing-v4-nfz-2s
uv run python -m benchmarks.run_productive_routing --input ../docs/benchmark-results/productive-routing-v3-physical/results.json --cases scale_restriction_physical --methods adaptive cells alns_fast sorties cells_sorties --seconds 8 --seeds 10 --output ../docs/benchmark-results/productive-routing-v4-nfz-8s
uv run python -m benchmarks.productive_summary --input ../docs/benchmark-results/productive-routing-v4-nfz-2s/results.json ../docs/benchmark-results/productive-routing-v4-nfz-8s/results.json --output ../docs/benchmark-results/productive-routing-v4-summary.json
```

`productive_summary` показывает медиану, минимум, максимум и p95, проверяет
SHA-256 снимков и одинаковый код алгоритмов в сравниваемых сериях.
Для парных разностей по seed относительно `alns_fast` дополнительно считает
bootstrap-интервал медианы. Он описывает разброс seed на этих задачах,
не переносимость результата на другие территории. Детерминированные методы
выполняются один раз на бюджет; стохастические — с 10 seed каждый.

## Проверка расписания, аудита и экспорта

```powershell
uv run python -m benchmarks.productive_pipeline --input ../docs/benchmark-results/productive-routing-v3-physical/results.json ../docs/benchmark-results/productive-routing-v4-nfz-2s/results.json ../docs/benchmark-results/productive-routing-v4-nfz-8s/results.json --cases scale_restriction_physical --output ../docs/benchmark-results/productive-routing-v4-pipeline.json
```

Адаптер восстанавливает известные условия бенчмарков и создаёт отдельные
`SURVEY` для каждого галса, `TRANSIT` между ними, один взлёт и одну посадку
на вылет. Используются штатные scheduler, safety auditor и четыре экспортера:
GeoJSON, KML, QGroundControl и Mission Planner. Проверяются baseline и
лучший по исходному критерию вариант из переданных отчётов. Параметры
`--methods` и `--criteria` позволяют проверить другого финалиста отдельно.
После scheduler исходный критерий пересчитывается с реальным makespan;
регресс относительно baseline не проходит локальный допуск. Это выбор
финалиста для проверки совместимости, а не оценка среднего качества по seed.

Дополнительные проверки независимо от штатного verifier считают покрытие
объединением отдельных съёмочных полос, сравнивают время на границах фаз
и разбирают команды камеры, включая фактические JSON/WPL-файлы экспортов.
Отдельная номинальная проверка сближений использует времена каждого плеча
с ветром и ограничением скорости съёмки; ядро closest approach общее со
штатным scheduler. Она не сертифицирует неопределённости, рельеф и вертикальные фазы.
Проверка скорости выявляет галсы, на которых
экспортируемая скорость на плече превышает допустимую путевую скорость
съёмки; проверяется действующее состояние команды скорости. Прохождение геометрического аудита само по себе
не устанавливает `integration_ready=true`.

Адаптер не подключает методы к HTTP-планировщику и не заменяет штатное
построение кандидатов. Наборы не кодируют произвольные эксплуатационные
условия: проверены известные параметры этих сценариев. Рельеф, окна
разрешений, разные базы, аварийные площадки и импорт в реальные версии
наземных станций требуют отдельной приёмки перед внедрением.

## Интерпретация

- Точный решатель служит эталоном распределения для небольших задач.
- Оптимальное распределение по построенным вариантам не доказывает глобальную
  оптимальность геометрии и расписания.
- Синтетические сценарии проверяют поведение модели и не заменяют полётные испытания.
- Структурная проверка экспорта дополняется импортом в применяемую версию
  QGroundControl, Mission Planner или другого целевого ПО.
- Пределы физической модели описаны в [допущениях о манёвренности](maneuverability-assumptions.md),
  семантика высот и времени — в [контракте геоданных](4d-geodata-contract.md).


## Повтор пятого цикла

Сравнение долей бюджета каталога (60% и 85%) на неизменной задаче:

```powershell
uv run python -m benchmarks.run_productive_routing --input ../docs/benchmark-results/productive-routing-v3-physical/results.json --cases scale_restriction_physical --methods cells cells_budgeted --seconds 2 --seeds 1 --deterministic-repeats 10 --output ../docs/benchmark-results/productive-routing-v5-catalog-2s
```

После исправления времени фаз сквозной отбор выполняется по штатному
расписанию. Для каждого метода проверяется лучший по загрузке вариант,
идентичные решения пропускаются. `--selection scheduled` сравнивает
проверенные финалисты с baseline после scheduler, `--selection load`
оставляет один предварительно выбранный финалист как контроль.
Плохой кандидат не вытесняет baseline; проваливший проверки baseline
не подставляется как безопасный. Список `selected` хранит итоговый выбор.

```powershell
uv run python -m benchmarks.productive_pipeline --input ../docs/benchmark-results/productive-routing-v4-nfz-8s/results.json ../docs/benchmark-results/productive-routing-v4-controls-8s/results.json --methods cells --selection scheduled --output ../docs/benchmark-results/productive-routing-v5-pipeline.json
```

Начиная с пятого цикла источники `backend/src/geoplan/` также копируются
в снимки с SHA-256. Для сквозного отчёта они находятся в одноимённом каталоге
`.source/`, снимок адаптера — в `.source.py`. Это фиксирует незакоммиченные
исправления, которые нельзя воспроизвести по одному Git HEAD.

## Пул длительностей вылетов

`productive_schedule_pool` проверяет гипотезу, что более короткие вылеты
могут уменьшить задержки разведения БВС. Он строит один каталог по порядку
`cells`, сохраняет разные полные разбиения без предварительного отбора по
загрузке, распределяет группы по парку и пропускает каждый вариант через
штатные scheduler, audit и четыре экспортера. Итог выбирается по исходному
критерию с реальным makespan; baseline остаётся допустимым кандидатом.

```powershell
uv run python -m benchmarks.productive_schedule_pool --input ../docs/benchmark-results/productive-routing-v3-physical/results.json --output ../docs/benchmark-results/productive-routing-v6-duration-matrix.json --criteria completion_time --targets 30 45 60 120 192
```

Команда запускается из `backend/`; выходной файл и каталог `.source/`
должны отсутствовать. Фильтр `--cases` позволяет проверить один сценарий.
`--catalog-seconds` и `--assignment-seconds` ограничивают отдельные стадии
генерации, **не** всё время поиска и сквозной проверки. Время генерации,
каждой проверки и всего сценария сохраняется раздельно. Полный перебор
расписаний дороже генерации маршрутов и пока предназначен для стенда.

`--targets` задаёт предел разбиения на представительном БВС, а не новый
физический предел для всего парка. После назначения на другой БВС длительность
может измениться; `longest_sortie_minutes` показывает фактический максимум.
Энергетический резерв и допустимость каждого вылета проверяются прежней
моделью. Недоступные разбиения и повторы записываются в `attempts`, а не
подменяются baseline. Поле `integration_ready` отражает проверки кандидата;
защита от ухудшения целевого критерия применяется при итоговом выборе.

Отчёт сохраняет решения, отдельные service/deadhead costs, фактический
makespan, физическую допустимость, результаты аудита и экспорта, SHA-256
входного набора и снимков `src/`, `benchmarks/`, `scenarios/`. Сокращение
makespan при росте холостого налёта считается компромиссом для критерия
`completion_time`; оно не означает улучшения `total_flight_time`.

Второй контроль сохраняет назначение БВС из каталога (`catalog`) вместо
распределения по предварительной загрузке (`load`). На текущих однобазовых
задачах каталог использует самый быстрый БВС, допуская его повторные вылеты
с прежним обслуживанием. Это проверка пользы параллельного назначения
при нынешней модели разведения, а не требование использовать один БВС.
`--allocations load catalog` сохраняет оба назначения, если решения различны.
`load` может также развернуть группу галсов при назначении; сравнение
проверяет сохранение исходного кандидата целиком и не изолирует только
влияние числа БВС.

```powershell
uv run python -m benchmarks.productive_schedule_pool --input ../docs/benchmark-results/productive-routing-v3-physical/results.json --output ../docs/benchmark-results/productive-routing-v6-catalog-assignment.json --criteria completion_time --targets 192 --allocations catalog
```

Начиная с контроля назначения, снимок также включает `pyproject.toml`,
`uv.lock` и версию Shapely. Ранние отчёты шестого цикла фиксируют Python и
Python-исходники; для окружения используется lock-файл текущего checkout.

## Свободная геометрия съёмки

Актуальная точка запуска — `benchmarks.run_frame_coverage`, проверяющий скрипт —
`benchmarks/verify_free_coverage.py`. Предыдущие отдельные драйверы геометрии,
равномерного замедления и попарного анализа удалены. Диагностика соседних кадров
теперь выполняется внутри основного запуска; одна проверка воспроизводит как
обычные маршруты, так и дополнительное локальное изменение времени.

Из корня репозитория, с отсутствующим выходным каталогом:

```powershell
uv run --directory backend python -m benchmarks.run_frame_coverage --suite holdout --profile 60:75 --output ../docs/benchmark-results/coverage-new
uv run --directory backend python benchmarks/verify_free_coverage.py ../docs/benchmark-results/coverage-new
```

Встроенные наборы не требуют файлов от предыдущих запусков:

| Параметр | Значение |
|---|---|
| `--suite holdout` | Шесть новых геометрий: круг, эллипс, разные площадки, U-область и узкая перемычка |
| `--suite reference` | Восемь исходных контрольных геометрий |
| `--suite all` | Оба набора |
| `--trigger-interval 1` | Интервал камеры в секундах; по умолчанию 1 с, как в интерфейсе |
| `--profile 60:75` | Боковое:продольное перекрытие; флаг можно повторять |
| `--case holdout_ellipse_cross_sites` | Оставить указанную геометрию; флаг можно повторять |
| `--timing-diagnostic` | Дополнительно проверить локальное изменение времени на каждом выбранном сценарии |

Без `--profile` проверяются 60:75, 50:75, 60:60 и 50:60. Разные профили
не смешиваются при оценке алгоритмического выигрыша. 75/60 — настройки по
умолчанию, а не установленное требование организаторов; по нашим записям
Q&A минимальное боковое перекрытие — 50%. Состояние исходных требований —
в [решениях по Q&A](expert-faq-decisions.md#происхождение-параметров-перекрытия).

Повтор на замороженных условиях:

```powershell
uv run --directory backend python -m benchmarks.run_frame_coverage --inputs ../docs/benchmark-results/coverage-new/inputs.json --output ../docs/benchmark-results/coverage-repeat
uv run --directory backend python benchmarks/verify_free_coverage.py ../docs/benchmark-results/coverage-repeat
```

`--inputs` сохраняет геометрию, камеру, площадки, ресурс, профили перекрытия
и идентификаторы из JSON. Вместе с ним нельзя задавать другой набор,
интервал камеры или `--profile`: повтор использует точные сохранённые условия.

### Алгоритмы и выбор

Контроли используют текущий генератор приложения и общий `geoplan.routing`,
перестановку проходов, вложенные контуры и внешний обход с прямым центром.
Смешанные варианты проверяют 1/3/5/8/9 контурных слоёв, два угла центра и
два порядка внутренних проходов. Новый `split_shell` делит каждый слой на
две дуги: на удалении и на выходе к посадке. Полный периметр сохраняется.
Ориентации проходов выбираются с учётом обеих площадок и ветра.

Основной победитель минимизирует налёт среди прошедших геометрический фильтр.
Дополнительно `best_endpoint_protected_family` выбирает минимум налёта,
не ухудшающий относительно допустимого исходного маршрута ни налёт,
ни суммарное camera-off время, ни подлёт, ни финальный возврат.
Если подходящего улучшения нет, остаётся исходный вариант.
В приложении эта политика применяется к свободным кандидатам после построения
реальных миссий и повторяется после расписания; стендовая строка не заменяет
сквозной расчёт. Общая геометрия и физическая проверка теперь находятся в
`geoplan.routing`, сценарии — в `scenarios.freeform`.

### Проверки и файлы результата

- `inputs.json`: точные условия и локальная проекция для каждого сценария;
- `results.json`: все кандидаты, явные фазы, метрики, SHA-256 входов/исходников,
  выбор по времени и выбор с защитой обоих концов;
- `summary.csv`: сводка, отдельное время генерации и проверки;
- `retiming-diagnostic.json`: дополнительные попытки локального времени;
- `source/`: снимок Python-кода, тестов, `pyproject.toml` и `uv.lock` до расчёта;
- `verification.json`: повторный расчёт метрик и выбора по архивным исходникам.

Проверяющий скрипт запускается в свежем процессе. Он сверяет хеши,
воспроизводит траектории, независимо восстанавливает часы камеры и выбор
победителей. Для локального времени повторяет сам поиск, причины отказа,
проверяет неизменность геометрии и camera-off фаз. Для исторических серий
используется скрипт из их собственного `source/benchmarks`, соответствующий
сохранённому протоколу; совместимость со старыми схемами в текущий код не добавляется.

Основной фильтр: полное объединение реальных снимков ≥99,99%, приближение
внутреннего эффективного шага ≥99,9%, GSD, аппаратный интервал камеры,
физическая скорость, непрерывность, запретные зоны и ресурс каждого вылета.
Попарная площадь кадров остаётся диагностикой, а не обязательным порогом.
Коридоры эффективной ширины — приближение бокового покрытия при меняющемся
направлении, а не доказательство фотограмметрического качества.

Стенд моделирует один БВС и плоскую территорию. Набор не подтверждает динамику,
нижнюю воздушную скорость, энергию вертикальных фаз, рельеф, окна и расписание
парка. Сокращение camera-off времени само по себе не доказывает отсутствие
лишних снимков; отдельно сохраняется прокси избыточной съёмки.
Актуальные числа — в [результатах](productive-routing-results.md), история
измерений — в [краткой истории](productive-routing-results.md#история-измерений).

Текущая итоговая серия — `free-coverage-v6-holdout-complete`, контроль камеры —
`free-coverage-v6-camera2`, точный повтор — `free-coverage-v6-repeat`.
Сводная проверка — `docs/benchmark-results/free-coverage-v6-validation.json`.
Предварительный `free-coverage-v6-holdout` не подменяет итоговый выбор
с защитой площадок. Числа и отрицательные результаты — в
[десятом цикле](productive-routing-results.md#десятый-цикл-новые-территории-и-размыкание-к-посадке).

## Сквозная проверка свободного покрытия

```powershell
uv run --directory backend python -m benchmarks.verify_freeform_pipeline --output ../docs/benchmark-results/pipeline-new.json
```

Команда вызывает настоящий HTTP-планировщик с выключенным и включённым
дополнительным пулом на шести одинаковых задачах. Проверяет аудит, отсутствие
ухудшения налёта, интервалы явных кадров и все четыре HTTP-экспорта.
`--case holdout_circle64` оставляет один сценарий. Выходной файл должен
отсутствовать. Компактные входы и исторические результаты включены в
`reference/benchmarks/`; для нового запуска игнорируемые локальные архивы не нужны.
Передача проекта описана в [итоге сессии](session-handoff.md).
