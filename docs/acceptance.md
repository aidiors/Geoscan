# Проверка масштаба и требований

Проверено 19 октября 2026 года. Базовая ревизия — `d1fe0ce`; изменения
30-минутного бюджета и исправление отбора маршрутов по ресурсу пока не закоммичены.
Сервис нельзя считать полностью прошедшим эксплуатационную приёмку:
крупные пакеты реальных контуров выявили ошибку построения покрытия.

[Контрольные данные, хеши и результаты отдельных запусков](../reference/benchmarks/service-acceptance-2026-10-19.json).

Временные полные ответы, запросы и логи в `work/` очищены по просьбе пользователя.
Контрольная сводка и хеши в `reference/` сохранены; для нового запуска стенд
восстанавливает входы из фабрик сценариев и исходного KML.

## Условия и воспроизведение

Проверки выполнялись настоящими HTTP-запросами к отдельным контейнерам,
без изменения операторских проектов. Docker: 16 CPU, 31,27 GiB памяти;
ограничения ресурсов контейнеров не задавались. Парк, камеры, площадки,
ветер и DEM в масштабных сценариях синтетические. В пакетах заказчика
реальны только контуры из исходного KML.

Драйвер сохраняет параметры, хеши кода, JSONL завершённых проверок,
точные запросы и сжатые ответы. Проверяет независимый аудит, снимки,
GIS-экспорт и архивы автопилотов, включая хеш каждого файла вылета.

```powershell
uv run --directory backend --locked --extra optimization python -u -m benchmarks.service_acceptance quality --url http://127.0.0.1:8002 --container YOUR_TEST_CONTAINER --output ../work/acceptance-quality.jsonl --budget 1800 --stream
uv run --directory backend --locked --extra optimization python -u -m benchmarks.service_acceptance load --url http://127.0.0.1:8002 --container YOUR_TEST_CONTAINER --output ../work/acceptance-load.jsonl --budget 60 --users 2 4 8
```

Стенд нужно запустить отдельно от рабочего сервиса. `--counts` без чисел
отключает реальные пакеты; `--names` выбирает конкретные сценарии.
Бюджет нагрузки 60 с намеренно отличается от максимальных 1800 с:
он проверяет конкуренцию и освобождение слотов без получасового ожидания.
Это не измерение длительной нагрузки нескольких получасовых заданий.

## Масштабные сценарии

Исходная серия выполнена до изменения бюджета, с пределом 270 с.

| Сценарий | Расчёт | Результат |
|---|---:|---|
| 100 км², 10 БВС, balanced, срок 180 мин | 12,93 с | Аудит пройден, 14 вылетов, срок 179,90 мин |
| 100 км², минимум срока | 14,52 с | Аудит пройден, 18 вылетов, срок 126,53 мин |
| 100 км², минимум налёта, срок 180 мин | 4,15 с | Аудит пройден, но срок 863,27 мин: условие срока не выполнено |
| 100 км², запреты, препятствия, ветер | 91,09 с | Аудит пройден, 112 вылетов, срок 412,12 мин |
| 100 км², DEM/AGL, ветер, временное окно | 270,00 с | Лимит времени до первого проверенного плана |
| 32 / 64 / 128 реальных полигонов | 64,04 / 74,56 / 100,63 с | Отказ `coverage_generation_failed`, участок `zone-316-2` |

Для трёх плоских вариантов проверены 46 287 кадров и 100% расчётного покрытия.
Для сценария с ограничениями — 78 856 кадров и 100% покрытия, но статус
фотограмметрической проверки `partial`: допущения модели не позволяют назвать
её полной физической проверкой. Конкретные предположения сохранены в результатах.

В варианте минимума налёта срок 180 мин был лишним ограничением тестового
запроса. Его отказ автопилотного экспорта 422 ожидаем при нарушенном сроке.
Повтор с бюджетом 1800 с и без срока прошёл за 4,30 с: первый проверенный
план за 0,49 с, аудит и все четыре формата пройдены.

Три размера реальных пакетов содержат один и тот же проблемный контур:
это три воспроизведения одного дефекта, а не три независимых класса ошибок.
Одиночная проверка исходного `zone-316` его не воспроизвела; причина в
контексте пакетного pipeline ещё не установлена. Небезопасный план не выдан.

Повтор DEM-сценария с бюджетом 1800 с завершился за 517,00 с (8 мин 37 с).
Первый проверенный план пришёл через 298,73 с, затем улучшен: срок работ
сократился с 496,69 до 464,90 мин. Итоговый аудит и 40 экспортов пройдены;
82 513 кадров, 100% расчётного покрытия, фотограмметрическая проверка `partial`.
Это успех в пределах нового бюджета, но почти пять минут до первого плана
не соответствуют ожиданию немедленной выдачи сложных заданий.

В этом запуске начальная стадия превысила свои 30 с до 47,06 с: пакет
кандидатов не проверял бюджет между отдельными оценками. Добавлены проверки
до и после оценки кандидата; воспроизведение с искусственными часами
подтверждает остановку после первого долгого кандидата. Измерения выше
относятся к образу до этого последнего исправления, что отмечено в данных.

На окончательной версии повтор завершился за **462,08 с (7 мин 42 с)**,
первый проверенный план — за **285,35 с (4 мин 45 с)**. Начальная стадия
заняла 30,02 с. Итоговые маршруты и метрики совпали с предыдущим запуском;
аудит, проверка снимков и 40 экспортов пройдены. Сообщение начала расчёта
пришло за 0,006 с. Быстрая передача состояния уже работает, быстрая первая
маршрутная выдача для этого сложного случая остаётся открытой задачей.
Разница времени единичных запусков не доказывает устойчивого ускорения.

## Поэтапная выдача и конечный парк

API и новые настройки интерфейса допускают 1–1800 с; по умолчанию — 30 минут.
Быстрая начальная стратегия ограничена 30 с, затем продолжается основной поиск.
Начало расчёта и сообщения активности передаются сразу, маршруты — после
независимого аудита. Публикуются только улучшения по исходному критерию.
Нельзя гарантировать первый маршрут сразу для любой геометрии или DEM.
Ранее сохранённый явно заданный бюджет проекта сохраняется.

На большой задаче с двумя комплектами АКБ на БВС обнаружен внутренний сбой:
в пул попадали каталожные варианты, превышавшие общий ресурс конкретного борта.
Исправлен приём кандидатов по канонической оценке ресурсов; регрессионная
проверка покрывает три критерия и ограничения в один/два активных БВС.
Повтор исходного запроса теперь возвращает диагностированный отказ
`unplannable_segment`. Это устранение сбоя, а не доказательство невозможности
найти допустимое распределение или успешная приёмка конечного парка на 100 км².

С четырьмя комплектами АКБ на борт (остаток ТО: пять вылетов и семь часов)
тот же масштаб прошёл: первый проверенный план за 1,56 с, итог за 20,44 с,
18 вылетов. Аудит ресурсов, качество кадров и четыре формата экспорта проверены.

**Для двух комплектов подтверждён пропуск допустимого решения.** План с
четырьмя комплектами фактически использует по одному/два комплекта на борт.
Его маршруты, расписание и команды камеры без изменений прошли полный
повторный аудит с исходным запросом на два комплекта и более строгим ТО.
Для проверки покрытия таблица групп восстановлена из опубликованных ID
миссий, их принадлежности области и шага полос; геометрия не подменялась.
Следовательно, возврат `unplannable_segment` здесь — недостаток эвристического
поиска, а не нехватка заданных ресурсов. Результат проверки-свидетеля сохранён
в контрольном JSON. Нужна доработка назначения/восстановления допустимости.

| Одновременные запросы | Приняты / занято 503 | Завершение принятых | Первый план в потоке | Health p95 |
|---:|---:|---:|---:|---:|

| 4 | 2 / 2 | около 35,6 с | 2,58 с | 0,152 с |
| 8 | 2 / 6 | около 32,7 с | Приняты JSON-запросы | 0,132 с |

У принятых запросов пройден аудит и совпали отпечатки соответствующих входов;
смешения результатов разных клиентов не обнаружено. Ошибок health на готовом
сервере нет. Пиковая **измеренная выборочно** память контейнера — 153,8 MiB.
После разрыва потока оба слота снова доступны примерно за 1,35–1,42 с.
Первая попытка двух клиентов попала на запуск контейнера и завершилась
обрывами соединения; она сохранена отдельно и исключена из таблицы.

В одном процессе разрешены два расчёта, остальные получают предложение
повторить запрос. Очереди нет. Это проверка контролируемой перегрузки,
а не готовности обслуживать восемь расчётов одновременно.

## Что необходимо до выпуска

1. Исправить пакетное покрытие проблемного контура и повторить 32/64/128.
2. Исправить пропуск допустимого назначения при двух комплектах АКБ;
   ускорить первый проверенный план на тяжёлом DEM.
3. Согласовать постоянный AGL и высотное разведение только транзитов.
4. Определить очередь/мощность для реального числа пользователей.
5. Проверить фактические профили БВС, исходные ограничения и импорт заданий
   в используемое полётное ПО; выполнить браузерную и операторскую приёмку.

Браузерная E2E-проверка на этой машине не подтверждена: отладочные подключения
Chrome запрещены политикой. Компонентные тесты, сборка и HTTP-проверки её
не заменяют. Паспортные данные конкретных моделей не перепроверены по свежим
руководствам производителя: обращения к PDF завершились ошибками доступа.

## Автоматические проверки

В зафиксированной серии прошли 602 backend-теста и 69 frontend-тестов,
проверки форматирования, типов, зависимостей модулей и документации. Результаты
относятся к исходникам контрольного JSON. Последующие изменения подложки карты
в эту серию не входят: по просьбе пользователя выполнены сборка и проверка
типов без запуска тестов.

На локальном сайте проверены health, опубликованный диапазон/значение
бюджета 1–1800 с и актуальная сборка интерфейса.

На тяжёлом HTTP-запросе с намеренно заданным бюджетом 1 с получен управляемый
`planning_time_limit` за 1,26 с без выдачи непроверенного маршрута.
Лимит кооперативный, сетевые расходы и отдельные неделимые операции остаются.
